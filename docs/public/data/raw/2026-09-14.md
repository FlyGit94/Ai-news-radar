### [vLLM v0.29.0 发布：Model Runner V2 成为全局默认](https://github.com/vllm-project/vllm/releases/tag/v0.29.0) ⭐️ 8.0/10

vLLM 发布 v0.29.0，包含来自 277 位贡献者（其中 91 位为新贡献者）的 594 次提交；Model Runner V2（MRV2）现已对所有模型默认启用，完成自池化模型开始的铺开，并新增用于 KV 缓存自动定容的 CUDA graph 内存剖析、把每步 logits 内存削减 1/TP 的 batch-sharded sampling、prompt embeds 以及 extract\_hidden\_states 投机解码等能力。新增模型集包括腾讯 770B/49B 激活的 Hy4-preview MoE（Gated DeepSeek Sparse Attention 与原生 MTP）、支持 BF16/FP8/NVFP4 与 MTP 的 Qwen3.8-Flash-Next、GraniteSWA 与 GraniteMoeSWA、带 MTP 的 NemotronH\_Omni\_Reasoning\_V3 以及 Kimi K3 NVFP4 检查点。性能上，Kimi-K3 与 DeepSeek V4 获得多项内核与并行优化（如 K3 Mamba 元数据准备合并为单次 Triton launch 带来 6.6–7.6 倍内核加速、调优的 Hopper 低延迟 GEMM 扩展至 SM100），投机解码增加按请求的接受统计（--per-request-spec-decode-metrics）与 SM100/SM90 稀疏 MLA 支持，Mamba 前缀缓存通过内部预填充检查点将 TTFT 改善 9%–25%；默认值方面 FlashInfer all-reduce 对 TP CUDA 组默认启用，前缀缓存 NONE\_HASH 默认确定化，并新增 --max-num-queued-reqs / --max-num-queued-tokens 准入控制参数。破坏性变更包括移除十个已弃用模型架构、FlexOlmo/Olmo3/Hunyuan V1/VL 迁移到 Transformers 建模后端、移除 PyAV 视频解码后端、弃用 python -m vllm.entrypoints.openai.api\_server 以及移除 VLLM\_TEST\_FORCE\_FP8\_MARLIN 与 VLLM\_ROCM\_USE\_AITER\_FP4\_ASM\_GEMM 两个环境变量。Model Runner V1 被列为弃用并计划在 v0.32 移除，序列并行、双批重叠、弹性专家并行、自定义 logits 处理器及部分投机解码方法在 MRV2 尚未支持前会回退到 MRV1。

### [跟随瓶颈：在 AMD MI355X 上优化 MiniMax M3](https://vllm.ai/blog/2026-09-10-minimax-m3-mi355x) ⭐️ 9.0/10

rss · vLLM Blog · 9月10日 00:00

**「背景」** MiniMax M3 已在 vLLM 上跑通 MiniMax Sparse Attention、多模态输入、MXFP8 权重与 EAGLE3，但作者真正关心的是：模型能跑之后，如何判断下一个优化点，因为瓶颈会不断移动。

**「方案」** 作者以“跟随瓶颈”为主线，围绕本地 M/N/K 形状、重复工作、字节移动、快路径是否真正执行以及扩展后哪个队列增长来展开。团队先用 PR 按实际本地形状选择 tile，把共享专家追加到路由专家表统一走 grouped GEMM，使并发 1 吞吐 +30.2%、并发 128 +5.6%；又让稀疏注意力跨层复用 top-k，在并发 1 使 TPOT 约降 10%，并把 128-token 逻辑块映射为 AITER 的 16-token 页表视图，避免复制 KV。EAGLE3 需要独立的缓存键和 draft 后端配置，多 token 验证也被扩展到 AITER。P/D 则先修好 KV 传输几何、写确认和异构 TP 确认，再调 worker 比例。公开结果中，MXFP8 固定拓扑并发 32 从 109.1 升至 342.4 tok/s/GPU（3.14×），并发 128 从 297.8 升至 623.7（2.09×）；MXFP4 并发 128 从 212.1 升至 716.8，后续 TP2 点达 943.5（4.45×，但拓扑不同）；EAGLE3 达 682.4；P/D 在并发 512 达 6370.5 total tok/s/GPU 与 1.32 秒 TTFT。作者强调这些检查点多为累积结果，只有孤立 A/B 才适合归因；他们还审计出 INT4 QuickReduce 的执行证据不足，并展示正确性门禁，例如修复 FP8 KV 视图使 GSM8K 从 0.0099 升到 0.9575。AgentX 首点达 127.4 输出 tok/s/GPU，理论前缀命中 96.7%、实际 92.1%，GPU KV 使用率 88.5%，提示下一步瓶颈可能在缓存、调度与 offload。

**「启示」** 作者的核心论点是：优化不是追逐单个吞吐数字，而是随瓶颈从 kernel/tile 上移到稀疏元数据、分布式状态、缓存与队列；每次获胜后都要重新 profile，并把正确性、预期快路径是否真正执行以及同合同端到端收益一起验证。

### [vLLM 分层 KV 缓存卸载：以主机内存为中心](https://vllm.ai/blog/2026-09-10-tiered-kv-offloading) ⭐️ 8.0/10

rss · vLLM Blog · 9月10日 00:00

**「背景」** 长上下文与多轮对话会生成庞大的 KV 缓存；当 GPU HBM 被填满，旧 KV 被驱逐，下次需要时只能从头重算。vLLM 自 v0.22 起提供的分层 KV 缓存卸载，把被驱逐的数据保留在主机内存、存储与远端节点，用重载代替重算。

**「方案」** 作者的核心设计是所有 KV 数据都经由主机内存（CPU DRAM）：卸载时先经 PCIe 拷到主机并立即释放加速器内存，再由主机并发级联到各二级层；重载时先提升到主机、数据就绪后才分配加速器内存，形成即时分配。主机侧采用规范化布局——每页存一层的一个块，跨 TP rank 的 KV head 聚成连续区域，定位只需偏移计算；该布局与 GPU 类型、注意力后端和并行配置无关，因此 TP=2 与 TP=4 节点产生相同的主机块，可直接共享。多卡分片合并为单一主机区域，把大量小传输合并为更少更大的 I/O；主机层本身是 LRU/ARC 缓存而非暂存区。二级层包括文件系统（内容寻址，共享挂载即自动共享）、经 NIXL 的 S3 兼容对象存储，以及用 ZMQ 协调、RDMA 传输的 P2P；P2P 不自行选择 peer，由编排层（如 llm-d）通过 kv\_transfer\_params 驱动，用于 prefill/decode 分离与负载均衡，且全程主机到主机，分块预填充让计算与传输重叠。框架还暴露 Prometheus 指标与 KV 事件，供外部路由器做缓存感知调度；二级层只需实现四个核心方法、通过 memoryview 直接读写主机区域，支持 out-of-tree 扩展。作者在 Qwen3.6-35B-A3B、2×H100、TP=2、本地 NVMe、12K 初始提示加 4K×8 轮、并发 64 的预填充吞吐测试中称：约 64 轮会话内 HBM 足够；64–128 轮时无卸载吞吐骤降而 CPU 卸载维持；超过 128 轮 CPU 也满，存储卸载仍保持高命中率并把吞吐提高一倍以上。

**「启示」** 作者认为，把主机内存作为规范化的中心层、配合内容寻址共享与合并 I/O，使 KV 缓存可跨节点横向扩展；规模化时“存储命中”对比“完整重算”仍是压倒性的选择。

### [vLLM 的 Hybrid HiSparse：GLM 5.3 稀疏 KV 卸载](https://vllm.ai/blog/2026-09-08-glm53-part1-hybrid-sparse-offloading) ⭐️ 8.0/10

rss · vLLM Blog · 9月8日 00:00

**「背景」** Agentic 负载下并发请求多、上下文持续增长，而 GPU block pool 固定，KV cache 终会耗尽。已有两条路各有代价：抢占丢弃 KV 并重新 prefill，每次驱逐都要重付一遍 TTFT；卸载把块搬到主机内存，但稠密注意力要求每个 token 都驻留 GPU，并发数仍受显存限制。

**「方案」** vLLM 的 Hybrid HiSparse 利用 sparse-MLA 的 indexer 只选 top-K token 这一点：未被选中的 KV 卸到 CPU，使每请求的显存占用有上界；indexer KV 仍驻留 GPU 且随上下文增长，但体量小得多，GLM 5.3 的 IndexShare 更让它每四层 sparse-MLA 才出现一次。Hybrid 的增量是把卸载变成按压力触发的驻留策略：请求在 full / mixed / no residency 三态间迁移，混合态下 block table 并存真实块与 null 占位、尾部永不驱逐，一个融合 kernel 解析 top-K，命中驻留页就地读取、命中热 token 则刷新其 LRU，未命中就从 pinned host memory 拷入一行，解码路径不等待 CPU 决策，因而仍可被 CUDA graph 捕获。关键在于热缓冲不是独立分配，而是经 vLLM Hybrid Memory Allocator 从同一池租用、位于同一 KV tensor 中的普通 KV-cache block，对 sparse MLA kernel 而言与普通页无异，一个请求释放的块可成为另一个请求的热缓冲。前缀页写完即排队拷往 CPU、同时继续由 GPU 服务，压力到来时可直接释放槽位；indexer KV 仍由标准 OffloadingConnector 独立卸载，P/D 导入与投机解码照常工作，热缓冲默认每请求 2×top-K 行。在 8×H200 上以 OpenHands 13 轮 agentic 负载实测（首轮 74,160 token，后续 753 token，固定 220 token 输出，TP8、MTP3、FP8 KV、142K 准入上限）：基线用 512 GiB 卸载池，Hybrid 把同一主机预算拆成 384 GiB HiSparse 池加 128 GiB 卸载。作者称这让 GLM 5.3 首次在该硬件上跑满 100 万上下文并显著提升各长度下的并发，但文中只引用图表、未给出数值。局限包括：MTP 的热缓冲需一次容纳全部验证 token，目前要按 \(num\_speculative\_tokens+2\)×top-K 规划；并发计算器给出的只是规划估计而非保证；HiSparse 目前仅支持 NVIDIA GPU，计划随 vLLM v0.30 发布。

**「启示」** 作者的结论是：只有真正被注意到的 token 才值得付出 CPU-GPU 搬运代价，把卸载做成按显存压力触发的驻留策略，请求便能在部分驻留下继续解码，而不是等待槽位或再次 prefill。

### [vLLM × AgentX：Agentic 推理服务的全栈优化](https://vllm.ai/blog/2026-09-08-vllm-agentx) ⭐️ 8.0/10

rss · vLLM Blog · 9月8日 00:00

**「方案」** vLLM 的优化横跨三层。数据面用统一内存页和共享块池的混合 KV 缓存管理器按需重分配，并把 DeepSeek V4 原本 92 个碎片张量改为打包布局，配合 FP4 indexer 省下约 10% KV 显存；Mooncake Store 提供分布式 KV 池与磁盘/CPU 分层卸载，再以“按间隔”和 Marconi 式“前缀二次出现即存检查点”两条保留策略维持高命中率。执行面上，Kimi K3 用解码上下文并行（DCP）分片 KV，并以对称内存把通信融进注意力内核，每层延迟约降 13%，但在 NVL72 级系统上宽 EP 加数据并行（DEP）更优；DeepSeek V4 因压缩稀疏注意力，PCP8 对 32K 提示的预填比 TP8 快 2.65×，而 DEP 成为多数配置的默认。调度上，用 --long-prefill-token-threshold（512）打断长预填的队头阻塞，使 TPGS 最高提升 93%、P90 交互性约 2.3×，代价是长请求 TTFT 上升；再用 --prefill-schedule-interval 对齐 DEP 各 rank 的预填节奏，并以两阶段饱和/扫描法匹配 P/D 比例。作者报告 DeepSeek V4 Pro 达 130K tokens/GPU 秒、MiniMax M3 达 376 tokens/s，相对 Opus 5 API 定价有 14.6×–106× 成本优势。作者也记录反面结果：流水并行不适合缓存已热的轮次，DCP 在 DeepSeek V4 上只追平 DEP，而按队列或 KV 利用率的负载均衡不如会话感知的粘性路由。

**「启示」** 作者的核心论点是：并行与调度必须服从模型架构和会话的缓存局部性；agentic 服务的成本优势源于极高的前缀复用，下一步是让会话结构等 agent 提示显式传入服务栈。

### [vLLM v0.29.0 发布，Model Runner V2 成为默认执行后端](https://github.com/vllm-project/vllm/releases/tag/v0.29.0) ⭐️ 8.0/10

vLLM 发布 v0.29.0，包含 594 个提交、277 名贡献者（其中 91 名新贡献者），最核心的变化是 Model Runner V2 成为所有模型的默认执行后端，完成了此前从池化模型开始的迁移；MRV1 随之被标记为弃用，目标是在 v0.32 中移除，且不再接受 MRV1 专属的改进或优化。新版本新增 Hy4-preview、Qwen3.8-Flash-Next、GraniteSWA/GraniteMoeSWA、NemotronH\_Omni\_Reasoning\_V3 与 Kimi K3 NVFP4 检查点等模型支持，并针对 Kimi-K3 与 DeepSeek V4 引入融合 MXFP4 top-k 收尾（约 5% 端到端延迟改善）、单次 Triton launch 的 Mamba 元数据准备（6.6–7.6 倍内核加速）等优化。Mamba 前缀缓存通过内部 prefill 检查点将 TTFT 改善 9%–25%，FlashInfer all-reduce 在 TP CUDA 组中默认启用（可用 VLLM\_ALLREDUCE\_USE\_FLASHINFER=0 关闭），并新增 --max-num-queued-reqs/--max-num-queued-tokens 准入控制参数。破坏性变更包括移除十个已弃用模型架构、移除 PyAV 视频解码后端，以及弃用 python -m vllm.entrypoints.openai.api\_server（改用 vllm serve）。由于序列并行、双批重叠、弹性专家并行、自定义 logits 处理器和部分投机解码方法尚未在 MRV2 中支持，配置这些功能时 vLLM 仍会回退到 MRV1，官方称相关缺口计划在接下来 2–3 周内补齐。

github · khluu · 9月9日 08:54

**「背景」** vLLM 是一个开源的大语言模型推理与服务引擎，其模型运行器（Model Runner）负责实际执行模型前向计算。Model Runner V2（MRV2）是对该运行器的一次从零重构，目标是让代码更清晰、更模块化、性能更高，且不改变现有 API。vLLM 在此前版本中先从池化模型开始逐步启用 MRV2，本次 v0.29.0 将 MRV2 设为所有模型的默认运行器，并开始将 MRV1 标记为弃用。

**「影响」** 使用序列并行、双批重叠、弹性专家并行、自定义 logits 处理器或部分投机解码方法的用户，在升级后会继续自动回退到已被弃用的 MRV1，需要在其计划于 v0.32 移除前跟踪这些功能的补齐进度；同时依赖被删除的十个模型架构、PyAV 视频解码后端或已移除环境变量的部署将无法直接升级。

### [trynix.dev：在浏览器中运行任意 Nix 包](https://simonwillison.net/2026/Sep/10/trynix/) ⭐️ 8.0/10

Simon Willison 介绍了 Farid Zakaria 打造的 trynix.dev，后者称其为自己在 Nix 工作上的“magnum opus”（代表作）。该站点通过 qemu-wasm 在浏览器中以 WebAssembly 运行一台 x86\_64 Linux 虚拟机，并能用过去 13 年间的任意 Nix 包启动它。这些包可 URL 寻址，例如访问 https://trynix.dev/?pkg=python3%403.6.2 并点击“Load”，就能进入一个运行 2017 年 Python 3.6.2 的交互式 shell。Farid 还基于此构建了 trynix-preview：这个 GitHub Action 会在 pull request 下评论一个链接，让评审者在浏览器里启动该 PR 的构建，无需服务器。

### [vLLM 的分层 KV 缓存卸载架构](https://vllm.ai/blog/2026-09-10-tiered-kv-offloading) ⭐️ 8.0/10

rss · vLLM Blog · 9月10日 00:00

**「背景」** 长上下文模型与多轮对话会产生庞大的 KV 缓存；GPU HBM 一旦占满，vLLM 只能驱逐旧数据并在下次请求时重新计算。作者介绍 vLLM 自 v0.22 起提供的分层 KV 缓存卸载：把被驱逐的 KV 保留在主机内存、存储和远程对等节点中，以重载替代重算，并让缓存可跨节点共享。

**「方案」** 其核心是主机中心设计：KV 数据总是先从加速器经 PCIe 拷贝到 CPU DRAM，再流向文件系统、对象存储或远端 peer，重载时反向进行；显存可在拷贝完成后立即释放，且只在数据就绪后分配，实现“及时分配”。各 TP rank 的 KV 分片被合并进一个共享主机区域，并排成规范化布局——每页保存一层的一块，跨 TP 的 KV 头连续，因此不同加速器、注意力后端或并行配置的节点也能直接共享，TP=2 与 TP=4 生成相同的主机侧块。操作以可配置大小的 chunk 为单位，主机层是 LRU/ARC 缓存；未命中时按顺序查询次级层，命中后异步提升回主机，调度器收到 RETRY 后重试。次级层包括内容寻址的文件系统、基于 NIXL 的 S3 兼容对象存储，以及以 ZMQ 协调、RDMA 传输且仅主机到主机的 P2P；P2P 拉取哪个 peer 由外部编排层决定，可用于 prefill/decode 分离与负载均衡。框架还以统一字节缓冲区支持全注意力、滑动窗口、MLA、Mamba 等混合层，暴露 Prometheus 指标和 KV 事件，并提供最小化的次级层接口，允许进程外实现。作者的基准（Qwen/Qwen3.6-35B-A3B、2×H100 TP=2、本地 NVMe 文件系统、12K 初始提示加每轮 4K、共 8 轮、并发 64、仅测 prefill 吞吐）显示：约 64 轮内 HBM 足够，64–128 轮时 CPU 卸载维持性能，超过 128 轮后存储卸载仍保持高命中率，吞吐较替代方案翻倍以上；但存储延迟更高，达不到峰值，不过仍优于完整重算。

**「启示」** 作者的核心结论是：分层卸载把“GPU 显存不够”转化为多级缓存问题，通过避免重复 prefill 提升有效服务容量，并借由共享主机布局把 KV 变成可跨节点迁移的数据；在规模化场景下，一次较慢的存储命中仍远胜一次完整重算。

### [vLLM 为 GLM 5.3 引入 Hybrid HiSparse 混合卸载](https://vllm.ai/blog/2026-09-08-glm53-part1-hybrid-sparse-offloading) ⭐️ 8.0/10

rss · vLLM Blog · 9月8日 00:00

**「背景」** GLM 5.3 体量大，单台 8×H200 显存本就吃紧；而 agentic 负载是大量并发的长上下文请求，GPU block pool 固定，KV cache 很快无块可分。此前要么抢占（preemption，请求每次被驱逐都要重付一次 TTFT），要么卸载到主机内存，但稠密注意力要求全部 token 驻留 GPU，并发上限仍受显存限制。

**「方案」** 作者转向稀疏 MLA：indexer 只挑出 top-K token 并仅对它们做注意力，因此可只让被选中的 KV 留在 GPU，其余卸载到 CPU，为每个请求的显存占用定出上界。Hybrid HiSparse 进一步只在显存吃紧时才卸载，请求按页在完全驻留、混合驻留、无驻留三态间迁移；混合态保留尾部，老页只留 CPU，indexer 需要的行放在热缓冲里，而热缓冲页与普通 KV 页取自同一 HMA 池和同一张量，对稀疏 MLA kernel 看来就是普通页。一个融合 kernel 解析 top-K：驻留 token 就地读，命中热缓冲则刷新 LRU，未命中从 pinned host memory 拷入一行，解码路径不等待 CPU 决策，因而仍可被 CUDA graph 捕获。前缀页写完即排队拷往 CPU 却继续由 GPU 服务，避免二次拷贝。作为共享 HMA 池上的驻留策略，它与 prefix caching、P/D 卸载和投机解码兼容，indexer KV 另由标准 OffloadingConnector 处理。评测在单台 8×H200 上用 OpenHands 十三轮 agentic 对话（首轮 74,160 token、后续 753、固定输出 220），TP8、MTP3、FP8 KV；基线为 512 GiB 卸载池，HiSparse 则是 384 GiB HiSparse 加 128 GiB 卸载。作者称这让 100 万上下文首次在该硬件可行并显著提高并发，但文中未给出具体数字；热缓冲默认 2×top-K 行/请求，MTP 下须按 \(num\_speculative\_tokens+2\)×top-K 配置，短上下文时热缓冲的固定开销反而使普通驻留更划算。

**「启示」** 作者的核心论点是：把显存视为可逐页让出的稀缺资源，只在内存压力下卸载稀疏注意力实际选中的行，比全量驻留或全量卸载更能支撑长上下文下的高并发——代价是热缓冲的固定开销与 MTP 带来的额外缓冲约束。
